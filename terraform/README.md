# Terraform - minimum Azure test environment

Provisions just enough to run and test the application:

```
resource group
├── AKS                2 nodes, Free tier, OIDC issuer + workload identity on
├── Key Vault          RBAC-authorized, holds the four application secrets
├── managed identity   federated to the External Secrets ServiceAccount
└── cluster add-ons    External Secrets Operator + ClusterSecretStore
                       ingress-nginx (provides the "nginx" IngressClass)
                       MongoDB (bitnami, 3-member replica set)
                       kube-prometheus-stack (Prometheus, Grafana, alerts)
```

MongoDB is installed by the same apply. Terraform generates its credentials,
composes the connection string and writes it to Key Vault, so there is no
manual `az keyvault secret set` step - the application gets a working URI from
the first apply. Set `enable_mongodb = false` and supply `mongodb_uri` to run
against a managed database instead.

## Layout

| Path | Purpose |
|---|---|
| `main.tf` | Resource group, secret generation, module wiring, workload identity |
| `modules/aks` | Single-pool cluster |
| `modules/keyvault` | Vault, RBAC role assignments, secret values |
| `modules/bootstrap` | Helm releases + the ClusterSecretStore chart |

The workload identity lives in `main.tf` rather than a module because it is the
join between two of them: its issuer comes from AKS and its role assignment
targets Key Vault.

## Use

```bash
cp terraform.tfvars.example terraform.tfvars   # set subscription_id
az login
terraform init
terraform apply
terraform output -raw next_steps
```

`next_steps` prints the exact commands for credentials, the ingress IP, the
registry pull secret and the two `helm upgrade` invocations.

## Things worth knowing before you apply

**State holds your secrets in plaintext.** `JWT_SECRET`, `FIELD_ENC_KEY` and
`BLIND_INDEX_KEY` are generated by `random_id` and written both to Key Vault
and to `terraform.tfstate`. That is a deliberate trade for a throwaway
environment - it makes one `apply` produce a bootable cluster. Do not reuse
this configuration for anything real without moving state to an encrypted
remote backend, or switching to secrets created out of band.

`terraform.tfstate` and `*.tfvars` are git-ignored.

**Key Vault RBAC is eventually consistent.** The vault module waits 60 seconds
between granting `Key Vault Secrets Officer` and writing secrets. Without the
wait the first apply intermittently fails with 403 even for a subscription
Owner, because data-plane permission is separate from control-plane.

**Being subscription Owner does not let you read the secrets.** With
`rbac_authorization_enabled`, Key Vault data actions need their own role.
Terraform grants `Key Vault Secrets Officer` to the identity it authenticates
as - which under service principal auth is the SP, not you. The portal then
shows *"The operation is not allowed by RBAC"* on the Secrets blade. Add your
own account to fix it:

```hcl
extra_secret_admin_object_ids = {
  me = "<az ad signed-in-user show --query id -o tsv>"
}
```

Or, for an already-deployed vault, out of band:

```bash
az role assignment create --assignee $(az ad signed-in-user show --query id -o tsv) \
  --role "Key Vault Secrets Officer" \
  --scope $(terraform output -raw key_vault_id 2>/dev/null || echo "<vault resource id>")
```

**The helm provider is configured from AKS outputs.** That works in a single
apply, but `terraform destroy` needs the cluster to still exist in order to
plan the helm releases. If you delete the cluster by hand first, remove the
releases from state (`terraform state rm module.bootstrap.helm_release...`)
before destroying.

**Secret names are a contract.** The Key Vault secret names are built from
`secret_prefix` and must keep matching the `remoteRef` keys in
`k8s/backend-values.yaml`. Key Vault permits only alphanumerics and dashes, so
they are dashed where the environment variables are underscored:

| Key Vault secret | Environment variable |
|---|---|
| `sg-bank-jwt-secret` | `JWT_SECRET` |
| `sg-bank-field-enc-key` | `FIELD_ENC_KEY` |
| `sg-bank-blind-index-key` | `BLIND_INDEX_KEY` |
| `sg-bank-mongodb-uri` | `MONGODB_URI` |

**External Secrets 2.x serves only `external-secrets.io/v1`.** The `v1beta1`
API is still in the CRDs but marked `served: false`, which is why
`helm-chart/templates/secrets.yaml` was moved to `v1`. If you pin an older
operator, that file has to move back.

**Sizing, and why node_count is 2.** The MongoDB replica set requests
`500m` per member at the chart's `small` preset - `1500m` across three - and a
`Standard_D2s_v6` has only `2000m` before kube-system, ingress-nginx, External
Secrets and the application take their share. One node cannot hold it. Two can,
and the regional vCPU limit on a trial subscription is typically 10, so 4 vCPU
is well inside quota.

To go back to a single node, either set `enable_mongodb = false`, or lower
`mongodb_resources_preset`. Be careful with the latter: `micro` gives a 384Mi
limit, and MongoDB's WiredTiger cache floor is 256MB, so the member is liable
to be OOM-killed under any real use.

A burstable B-series would be cheaper, but a VM size has to pass two separate
checks and the B-series fails one of them on this subscription:

```bash
# 1. is the SKU restricted for the subscription?
az vm list-skus -l westeurope --resource-type virtualMachines --all false \
  --query "[?name=='Standard_D2s_v6'].name" -o tsv

# 2. does its family have quota in the region?
az vm list-usage -l westeurope -o table | grep -i dsv6
```

`Standard_B2ms` is not offered at all; `Standard_B2s_v2` passes check 1 but its
`Standard Bsv2 Family vCPUs` quota is `0`, so it fails check 2 with a 400
part-way through the apply. Run both checks before changing this value.

## Monitoring

`kube-prometheus-stack` runs in the `monitoring` namespace. Grafana is
**ClusterIP only** and deliberately not on the public ingress — an
admin-credentialed dashboard on a nip.io host would undo the rest of this
setup. Reach it with a port-forward:

```bash
kubectl -n monitoring port-forward svc/kube-prometheus-stack-grafana 3000:80
# http://localhost:3000, user "admin"
az keyvault secret show --vault-name <vault> \
  --name sg-bank-grafana-admin-password --query value -o tsv
```

**Where the application signal comes from.** The API is not instrumented — it
exposes no `/metrics` — so application-level monitoring comes from
ingress-nginx's own metrics instead, which need no change to the app:

| Demo action | Dashboard shows |
|---|---|
| Repeated failed logins | 401 rate climbing |
| Push past the rate limiter | 429s appear |
| Wrong origin, missing CSRF token | 403s |
| Delete a pod | restart count, readiness gap, alert fires |

The structured event codes the API logs (`AUTHENTICATION_FAILED`,
`ACCOUNT_LOCKED`, `CORS_DENIED`, …) are **log** signals, not metrics, so they
stay in `kubectl logs` and do not reach a dashboard. Surfacing those would need
Loki, or `prom-client` in the application.

**The setting that decides whether any of this works.**
`serviceMonitorSelectorNilUsesHelmValues` defaults to `true` in the chart,
which restricts Prometheus to ServiceMonitors carrying its own release labels.
Left alone, ingress-nginx's ServiceMonitor is created and then never scraped —
empty panels, no error, nothing in any log. It is set to `false` here. If the
ingress dashboard is ever blank, check Prometheus → Status → Targets first:

```bash
kubectl -n monitoring port-forward svc/kube-prometheus-stack-prometheus 9090
# http://localhost:9090/targets - look for an ingress-nginx target UP
```

**Ordering.** The stack installs before ingress-nginx, because the
`ServiceMonitor` kind does not exist until the Prometheus Operator CRDs are in
place. That dependency is explicit in `modules/bootstrap/main.tf`.

**Footprint.** Storage is left unset, so Prometheus and Grafana use emptyDir —
no extra PVCs, faster bring-up, and metrics are lost on restart, which suits a
demo. Retention is 6h rather than the chart's 120h. If pods start going
`Pending`, the levers in order: lower `mongodb_resources_preset` to `micro`,
raise `node_count` to 3 (regional quota is 10 vCPU), or set
`enable_monitoring = false`.

## Teardown

```bash
terraform destroy
```

`purge_soft_delete_on_destroy` is enabled, so the vault is purged rather than
left in soft-delete to collide with the next apply. Purge protection is off for
the same reason - do not carry that setting into a production configuration.
